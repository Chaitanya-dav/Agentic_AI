# PROJECT

Agentic AI–Driven Secure Approval and Execution System

The system is based on a secure approval protocol with:

* canonicalisation
* SHA-256 payload hashing
* suspension/checkpointing
* approval notification/claim
* approval token containing BOTH payload_hash and approval_id
* resume with concurrency protection
* two hash comparisons
* four-eyes enforcement
* expiry validation
* boundary/policy re-evaluation at resume
* protection against tampering, replay, expiry and self-approval
* prevention of duplicate execution under concurrent approvals

IMPORTANT ARCHITECTURAL PRINCIPLE:
Do NOT allow an LLM/AI agent to directly override cryptographic or deterministic security controls.

Use Agentic AI for orchestration, analysis, investigation, risk explanation and workflow decisions.
Use deterministic code for final security enforcement.

# AGENT ARCHITECTURE

Implement four logical agents:

1. ACTION ANALYSIS AGENT
   Responsibilities:

* Accept natural-language action requests.
* Extract structured fields such as:
  action_type
  amount
  currency
  recipient
  creator
  description
* Normalize/canonicalize the action.
* Calculate the SHA-256 payload hash through a deterministic tool.
* Estimate risk and explain why approval is required.
* Return structured JSON.

The LLM should NOT calculate hashes itself.
It must call a deterministic hashing tool.

2. APPROVAL ORCHESTRATOR AGENT
   Responsibilities:

* Receive the structured action.
* Determine whether approval is required.
* Determine the required approver role.
* Create a unique approval_id.
* Create an approval request.
* Enforce four-eyes policy:
  creator_id MUST NOT equal approver_id.
* Maintain approval state.

3. SECURITY VERIFICATION AGENT
   Responsibilities:

* Verify an action before execution.
* Call deterministic security tools to check:

  1. current payload hash
  2. checkpoint payload hash
  3. token payload hash
  4. approval_id
  5. expiry
  6. creator/approver separation
  7. approval status
  8. whether approval has already been consumed
  9. current policy/boundary conditions
* Produce a human-readable explanation of the decision.
* The agent may investigate and explain, but deterministic security functions make the actual PASS/REFUSE decision.

4. EXECUTION AGENT
   Responsibilities:

* Execute an action ONLY when the security verification result is valid.
* Use a database transaction.
* Ensure exactly-once execution.
* Mark the approval as CONSUMED.
* Record the execution in audit logs.
* If verification fails, do not execute.

# CORE SECURITY PROTOCOL

Every action must be canonicalized before hashing.

Example canonical representation:

amount=50000|currency=INR|recipient=RAVI|action_type=PAYMENT

Calculate:

SHA256(canonical_payload)

Store:
payload_hash

When approval is created, generate:

approval_id

The approval token must logically contain:

{
"approval_id": "...",
"payload_hash": "...",
"expires_at": "..."
}

CRITICAL:
Never bind approval only to payload_hash.

Two genuinely identical actions can have the same payload_hash but MUST have different approval_id values.

Therefore execution must require:

token.payload_hash == current_payload_hash

AND

token.approval_id == stored_approval_id

AND

checkpoint.payload_hash == current_payload_hash

AND

approval is not expired

AND

approval is not consumed

AND

creator_id != approver_id

AND

current policy boundaries are satisfied.

# CONCURRENCY

Implement protection against two simultaneous execution requests.

The system must guarantee:

Two simultaneous attempts using the same approval
↓
Only one execution
↓
Second attempt is rejected as already consumed.

Use a transactional database operation.

Document that SQLite is used for the demo and production deployment should use PostgreSQL row locking/SELECT FOR UPDATE.

# SUSPEND AND RESUME

Actions must not immediately execute after creation.

Workflow:

CREATE ACTION
→ CANONICALIZE
→ HASH
→ CREATE APPROVAL
→ SUSPEND
→ SAVE CHECKPOINT
→ HUMAN APPROVAL
→ RESUME
→ RE-VALIDATE EVERYTHING
→ EXECUTE OR REFUSE

The checkpoint must contain enough information to verify that the action has not changed.

# BOUNDARY RE-EVALUATION

At resume time, do NOT assume that an approval is still valid simply because it was previously approved.

Re-run current policy boundaries.

Create a simulated environment containing values such as:

risk_level
recipient_status
daily_limit
account_status
transaction_limit

Example:

Monday:
risk_level = LOW
recipient_status = TRUSTED

Approval succeeds.

Later:
risk_level = HIGH
recipient_status = BLOCKED

On resume, the security system must refuse execution.

Display:

"Approval was cryptographically valid, but execution was refused because current policy boundaries changed."

The dashboard MUST include buttons to demonstrate four attacks.

ATTACK 1: TAMPERING

ATTACK 2: REPLAY ACROSS IDENTICAL APPROVALS

Create two genuinely identical actions:

Action A:
₹10,000 → Ravi
approval_id = A001

Action B:
₹10,000 → Ravi
approval_id = A002

They should have the same payload_hash but different approval IDs.

Attempt to use A001's approval token for Action B.

Expected:

payload_hash check = PASS
approval_id check = FAIL

Result:
REFUSED — APPROVAL REPLAY / APPROVAL ID MISMATCH

This attack is mandatory and must clearly demonstrate why binding only the payload hash is insecure.

ATTACK 3: EXPIRY

Create and approve an action.

Set expiry to a time in the past or use a simulation clock.

Attempt execution.

Result:
REFUSED — APPROVAL EXPIRED

ATTACK 4: SELF-APPROVAL

Alice

Result:
REFUSED — FOUR-EYES POLICY VIOLATION
